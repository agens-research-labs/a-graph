# Instructions for coding agents

How to work on a-graph, for people and agents alike. `CONTRIBUTING.md` says how to build and test.

## Commits and branches

- Never commit on `main`. Work on a branch named `type/short-kebab-description`.
- Message format: `type(scope): description`, then a blank line, then an optional body.
- `type`: feat | fix | docs | test | refactor | perf | chore.
- `scope`: mandatory, lowercase, one of: service, network, models, gate, run, graph, loader, schema, resources,
  external, logging, blackboards, embeddings, utilities, error, docker, examples, docs, readme, ci, deps, release.
- `description`: imperative, lowercase, no final period, 50 characters at most.
- Body: optional, most commits have none. When written: why, not what, lines under 72 characters. Mandatory only
  for an incompatible change: `BREAKING CHANGE:` on its own line in the body, and `!` after the scope in the title.
- One change per commit. Documentation changes in the same commit as the code they describe.
- Run `cargo fmt` before every commit.
- Never write: issue or ticket numbers, `Co-authored-by`, "Generated by", emoji, or any mention of the tool that
  wrote the commit.
- Do not push and do not open pull requests unless explicitly told to.

## Before a pull request

- The checks of `CONTRIBUTING.md` pass by hand: `cargo fmt --check`, `cargo build --locked`,
  `cargo clippy --all-targets --locked -- -D warnings`, `cargo test --locked --no-fail-fast`.
- A change to the routes or the answers of the service regenerates the spec:
  `cargo run -- --print-service-api > spec/service.openapi.json`.
- The docs in `docs/` say what the code does after the change.

## Reviews

- When reviewing, for every change of state answer: what happens between two events, who else writes the same
  resource, what is left if the process dies halfway, what happens to data written by the previous version, whether
  another open pull request touches the same flow, whether the shipped configuration (`service.yml`, `compose.yml`)
  turns the feature on, and which line of code keeps each promise of the docs.
- Do not trust a passing test for a race: reason on the order of the events.
- Say what you checked and what you could not check. Never state a commit, a line or a result you did not read.
